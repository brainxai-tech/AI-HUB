# ADR-001: Use DeepSeek as the Tarot Report Generator

## Status

Superseded by ADR-002

## Date

2026-06-15

## Context

The original AI Tarot Sanctum MVP was documented as a fully local rule-based tarot reader with no API key requirement. The current implementation has evolved: local code still owns the tarot deck, three-card draw, position assignment, upright/reversed orientation, local history, and review state, but the user-facing interpretation is generated by DeepSeek through `app/api/deepseek-reading/route.ts`.

Keeping the old "no API key, local rule-only" documentation creates a mismatch between product behavior and developer expectations.

## Decision

Treat DeepSeek as the product's tarot copy interpretation and judgment-report generation layer.

The current main flow is:

1. The browser collects the theme and question.
2. Local code draws three unique cards and assigns root, present, and trend positions.
3. The browser sends the structured reading, DeepSeek API Key, and model name to the local Next.js API route.
4. The route requests strict JSON from DeepSeek.
5. The route normalizes the returned report before sending it back to the UI.
6. The browser renders and optionally saves the reading in localStorage.

The deterministic local interpretation engine remains in the repository for tests, legacy compatibility, and possible fallback work. It is not the primary report generation path in the current UI.

## Alternatives Considered

### Return to Pure Local Rule Generation

- Pros: No API key, no network dependency, simpler privacy story.
- Cons: Lower output variety and weaker long-form report quality.
- Rejected for now because the intended product direction is to use DeepSeek as the report writer.

### Make DeepSeek Optional With Local Fallback

- Pros: Better resilience when no API key is available.
- Cons: More product states, more QA, and possible mismatch between local and AI report styles.
- Deferred. The local engine can support this later, but the current product behavior requires DeepSeek configuration.

## Consequences

- README and planning docs must say that DeepSeek API configuration is required.
- "Local-only" should not be used to describe the full product behavior. Use "local-first" or "local spread generation" instead.
- Privacy copy must be precise: saved readings and API configuration are localStorage-based, but report generation sends the structured reading and API credential to DeepSeek through the local API route.
- Tests should continue covering both the local engines and the DeepSeek route.
