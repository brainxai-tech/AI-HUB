## Product Summary

AI Tarot Sanctum is a local-first tarot reading website with a ceremonial, "tarot sanctum" feel. The current product focuses on relationship and career/wealth questions. Users choose a theme, write or select a question, perform a short shuffle-and-draw ritual, and receive a three-card reading report generated by a compatible AI model from a locally generated tarot spread.

The product should feel like an intentional tarot experience, not a generic AI chat wrapper. The local app owns deck data, card drawing, spread positions, history, and review state. The compatible model layer is used as a tarot copy interpretation and judgment-report generator. The current implementation requires a user-provided compatible API Key and internet access for report generation, but it does not require user accounts, a remote database, or cloud sync.

## Current Implementation Update

Date: 2026-06-17

The original MVP direction was local-only rule-based interpretation with no API key. That decision has been superseded by the current compatible-AI report generation flow:

- Local code draws three unique cards from the 78-card deck.
- Local code assigns root/present/trend positions and upright/reversed orientation.
- Local code sends the structured reading to the local Next.js API route.
- The API route calls the selected provider and requires strict JSON output.
- The compatible model writes the user-facing judgment report: clear answer, confidence, why, action steps, support/resistance signals, change condition, card sections, risk notes, and disclaimer.
- Browser localStorage still owns API configuration, saved readings, review tags, feedback, and notes.

The deterministic local interpretation engine remains in the codebase for tests, compatibility, and possible fallback work. It is not the primary UI generation path in the current implementation.

## Goal

Build a local web MVP that lets a user complete a three-card tarot reading for relationship or career/wealth questions, receive a coherent compatible-model judgment report based on the locally drawn spread, and optionally save the reading to browser local history.

Success evidence for the first implementation:

- The app runs locally from `01-Projects\ai-tarot-sanctum`.
- A user can choose relationship or career/wealth, enter a question, draw three cards, and see a result.
- The result includes a clear answer, confidence, per-card meanings, support/resistance signals, change conditions, risk notes, and action advice.
- Compatible API configuration is required before report generation and is stored only in browser localStorage.
- History is saved locally in `localStorage` and can be viewed or cleared.
- Core reading engine and interpretation engine have automated tests.
- The UI is responsive on mobile and desktop and keeps the actual tarot tool as the first screen.

## Target User

The first target user wants a private, atmospheric tarot reading for emotional or practical reflection. They are not looking for a professional divination system with every spread and occult correspondence. They want an experience that is fast, beautiful, repeatable, and readable.

## MVP Scope

In scope:

- One local Next.js app.
- Two reading themes: relationship and career/wealth.
- One primary spread: three cards mapped to root cause, present situation, and trend.
- No secondary quick mode in the MVP; the first release should focus on the three-card flow.
- Local card deck data with upright/reversed meanings.
- Compatible AI report generation from local structured reading data.
- Local rule-based interpretation engine retained for deterministic tests, compatibility, and possible fallback.
- Shuffle/draw interaction with short ritual animation.
- Result page with card details, combined reading, risk reminder, and next actions.
- Local reading history in `localStorage`.
- Basic accessibility, keyboard usability, reduced-motion support, and responsive layout.

Out of scope for MVP:

- Accounts, authentication, cloud sync, database, or payment.
- Generic AI chat mode unrelated to the drawn spread.
- Celtic Cross or other large spreads.
- Full tarot learning course.
- Social sharing image generation.
- Claims of deterministic future prediction or professional advice.

## Recommended Approach

Use the "Three-Card Sanctuary" approach.

The user selects a topic, writes a question, then draws three cards. The three card positions are:

1. Root cause: what is shaping the question underneath the surface.
2. Present situation: what energy or conflict is active now.
3. Trend: what direction the situation tends toward if the current pattern continues.

This approach gives enough depth to feel meaningful while staying small enough for a polished local MVP.

## Data Model

Card data should include:

- `id`
- `arcana`: major or minor
- `suit` for minor cards
- `name`
- `keywords`
- `upright`
- `reversed`
- `relationshipMeaning`
- `careerMeaning`
- `risk`
- `advice`

Reading data should include:

- `id`
- `createdAt`
- `theme`: relationship or career
- `question`
- `cards`: three drawn card results with position and orientation
- `summary`
- `actions`

The history format should be explicit enough to allow future migration. Unknown or malformed history items should be ignored rather than crashing the app.

## Interpretation Rules

The compatible-model prompt and local rule/fallback engine should preserve three interpretation layers:

1. Single-card layer
   - Uses theme, position, orientation, and card data.
   - Avoids generic encyclopedia text.
   - Example: a reversed Lovers card in the present relationship position should discuss avoidance, choices, or value mismatch rather than only saying "Lovers reversed."

2. Combination layer
   - Reads the whole spread.
   - Uses signals such as number of reversed cards, major arcana count, suit distribution, and card position contrast.
   - Example: many reversed cards means resistance, delay, or unclear motives; many major arcana means the issue is a larger stage-level lesson.

3. Action layer
   - Outputs three practical notes:
     - one next action
     - one mistake to avoid
     - one 7-day observation point
   - Relationship readings emphasize communication, boundaries, observable behavior, and emotional clarity.
   - Career/wealth readings emphasize opportunity filtering, timing, resources, risk, and execution.

Tone:

- Use "tendency", "signal", "reminder", and "possible direction" language.
- Do not claim certainty.
- Include a short disclaimer that readings are for reflection and entertainment, not professional advice.

## User Experience

The first screen is the actual tarot tool, not a landing page.

Primary flow:

1. User opens the app.
2. User selects relationship or career/wealth.
3. User enters a question or chooses a suggested prompt.
4. User starts the shuffle ritual.
5. User draws three cards.
6. Cards reveal into root cause, present situation, and trend positions.
7. Result scrolls in as a parchment-like reading panel.
8. User can save the reading, ask another question, or view local history.

Visual direction:

- Dark lacquer surface.
- Gold linework.
- Card backs with occult geometric motifs.
- Parchment-style result panel for readability.
- No decorative orb/blob backgrounds.
- No marketing hero page.
- The brand/product signal "三牌圣殿" or "Tarot Sanctum" appears immediately in the first viewport.

Interaction direction:

- Ritual animation should last about 2-3 seconds.
- Provide reduced-motion support.
- Keep controls touch-friendly.
- Result text should be readable on mobile and desktop.
- Long text should wrap cleanly and never overlap controls.

## Components

Suggested components:

- `QuestionAltar`: question text area plus suggested prompt chips.
- `DeckRitual`: shuffle state, draw cards, animation controls.
- `SpreadBoard`: three stable card positions.

Use stable sizes for card slots and controls so reveal states do not shift layout.

## Error Handling

Handle these states explicitly:

- Empty question: allow suggested prompts or show inline validation.
- Very long question: limit or gracefully truncate display while retaining the original in history if reasonable.
- No cards drawn yet: show an intentional empty altar state.
- localStorage unavailable: app still works for current reading and shows "history unavailable".
- Malformed saved history: ignore invalid entries and keep valid ones.
- Reduced-motion preference: replace shuffle animation with a short fade/reveal.

Errors should be shown near the relevant control, not only at the top of the page.

## Testing Plan

Automated tests:

- Reading engine draws exactly three unique cards.
- Orientation assignment is valid.
- Position assignment is root cause, present, trend in order.
- Reading engine accepts an injectable RNG so tests can produce stable results.
- Interpretation engine returns required sections for both themes.
- Combination layer reacts to reversed-card count and major arcana count.
- History parser ignores malformed records and preserves valid records.

Manual/browser verification:

- Complete relationship reading from start to result.
- Complete career/wealth reading from start to result.
- Save a reading, reload, and confirm it appears in history.
- Clear history.
- Check mobile width around 375px.
- Check desktop layout.
- Check reduced-motion behavior.

## Implementation Boundary

The first implementation should build only the local MVP. It should not add API configuration, cloud storage, social sharing, payment, or advanced spreads. The strongest first release is a polished and coherent three-card reading experience.

## Open Risks

- Rule-based text can feel repetitive if the card data and templates are too thin. Mitigation: write enough theme-specific meanings and vary phrasing by position/orientation.
- Full 78-card data takes time. Mitigation: still model all 78 cards, but keep first-pass meanings concise and structured.
- Overly mystical language can reduce trust. Mitigation: pair atmosphere with grounded "signals and actions" language.
- Animation can become distracting. Mitigation: keep it short and respect reduced motion.
